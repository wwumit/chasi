# 跨组织 agent 治理 —— 架构层

> 状态：架构稿（v0.3）
> 日期：2026-10-03
> 定位：本族的**架构层**——位于各分册之上一个层面。它回答**为什么这一族是这样分层的**；各分册回答**什么必须成立**。
> **本文档只陈述原则与约束。** 凡需要“必须”的地方，一律指向拥有该条的分册。见 §1.1——正是这条规则，使两层不会变成两份真相。
> **与身份绑定的关系。** 本层不自行陈述任何身份要求。它只预设主体**可跨域被标识**，并把 **`did:cha2a` 作为工作示例**——本族各分册即针对它书写（实验性草案 v1.1.0，已记入 W3C DID Extensions 注册表）。要求随绑定本身；更换示例不需要改动本页任何内容。
> 关联：`organization-governance.md` · `group-collaboration.md`（本仓库）· `overview.md` · `agent-identity.md` · `evidence-record.md` · `did-method-cha2a.md`（身份内核，另一仓库）· 《CHA2A Protocol Suite Architecture》（本层的上一层）

## 0. 本层的核心主张

> **Organization 是治理主体，Group 是协作主体。**
> **治理边界与协作边界分开表达，且两者都不预设一个中心信任根。**

展开：一个 agent 可以同时属于一个 Organization、参与多个 Group；在每个上下文里，**它代表谁**是可验证的，而不是由平台数据库断言。

**为什么本层需要自己的主张**：它是 §3 对象、§4 三个层面、§5 权威形状、§7 约束的判据。没有它，每一个被提议进模型的物件看起来都一样值得保留。

**本族三个主张的关系**——它们在不同层面，且不得互相矛盾：

| 层面 | 主张 | 它讲的是 | 所在 |
|---|---|---|---|
| `protocol-suite-architecture.md` | 互认不改任何一方的信任根；证据不靠运营方 | **承诺** | 本仓库（本族的上位架构） |
| **本文档** | Organization 是治理主体、Group 是协作主体；两个边界分开表达；不预设中心根 | **形状** | 本仓库 |
| `overview.md` §1 | 一个不属于任何一方的验证方能独立回答四个问题 | **验证方拿到的保证** | 身份内核，另一仓库 |

若某项改动使这三句里的任何一句不成立，那是**架构变更**，不是细节。

## 1. 本文档的地位

### 1.1 本层与各分册的分工

这条规则使同一个治理模型不会有两种描述：

| 层 | 只讲 | 越界 |
|---|---|---|
| **架构层**——本文档 | 为什么这样分层 · 对象模型 · 核心原则 · **跨分册的对核心设计约束** | 出现“必须 / 应当” |
| **规范层**——各分册，以及所用的身份绑定 | 什么必须成立 · 对象、字段、规则，以及每一条的推导 | 出现“因为这一族是这样分层的” |

**两边冲突时：规范性的内容以分册为准，“为什么”以本文档为准。** 关于**什么必须成立**的分歧是**缺陷，要修**，不是一种可以长期共存的状态。

### 1.2 本层的够用判据

**当仅凭本文档即可回答以下四问，本文档即为完备：**

1. 为什么 Organization 与 Group 是两个主体，而不是一条层级；
2. 为什么不预设中心信任根，以及由此推出什么；
3. 哪个对象需要可验证身份，什么时候需要；
4. 核心数据模型不得关死什么。

超出这四问的，都是规范工作，属于某一分册。

## 2. 核心原则

每条原则都附**它定下什么**——而不是任何人必须做什么。

| # | 原则 | 它定下什么 |
|---|---|---|
| 1 | **Local-first, federate-on-demand** | agent 在本地身份上运行。是跨主体互操作触发更强的身份能力，不是反过来 |
| 2 | **Identity ≠ DID** | 每个 agent 都需要**可识别的身份上下文**；**DID 是该上下文升级为跨域可验证形态**。这就是为什么一个对象可以早就存在、早就被指称，却还没有 DID |
| 3 | **Organization = 信任 / 治理域** | Organization 是**能被整体信任或不被信任**的单位，也是任命与撤销的单位 |
| 4 | **Group = 协作域** | Group 是一个**工作范围**，不是子组织。它可以跨组织、比其中任何一个活得久，并且可以由**任务发起方**而不是某个权威创建 |
| 5 | **Role = 权限上下文；Delegation = 授权关系；Representation = agent 在特定上下文中代表谁** | 这是三件不同的事；把它们混为一谈是权限类缺陷的常见来源 |
| 6 | **Registry = 发现与解析基础设施；信任锚是验证方自己的解析器** | Registry 是记录被找到的地方。验证方信任的是**它配置的那个解析器**——这也正是迁移之所以可能的原因 |
| 7 | **Runtime-neutral** | 这里没有任何一处依赖特定的 Agent Runtime、模型厂商或托管平台 |
| 8 | **治理边界与协作边界分开表达** | 每一条边界只在其自身范围内赋予资格：Group 内的角色来自 Group，组织内的角色来自组织 |
| 9 | **信任根留在原地** | 允许 Registry 迁移、允许多个 Registry 并存；**任何实现都不得把跨域信任建立在其自身注册表能解析该记录这一条件之上** |
| 10 | **记录比它的上下文活得久** | 成员资格、职位、组织终结时，历史证据存续——记录**反映变化** |

**这些原则在哪里变成要求**：2、3、8、10 在 `organization-governance.md` 与 `group-collaboration.md`；1 与 9 在 `group-collaboration.md` §9 与 §4.5；6 在**所用身份绑定的解析器契约**——工作示例中即 `did-method-cha2a.md` §4.1。

## 3. 对象模型

这个模型有**两个平面**，它们是对**同一批对象的两个视角**：治理平面与协作平面彼此平行，Group 也不持有任何组织的内部。

```
治理平面 —— 谁可以行事，代表谁

        Principal / Controller
                 │
                 ▼
            Organization
        ┌────────┼─────────┐
        ▼        ▼         ▼
      Admin   Policies   Agents
        │                  │
        └─── Delegation ───┘     （一种关系，不是汇报线）


协作平面 —— 谁在一起做事，在什么范围内

              Group
                │
                ▼
         Membership / Role
                │
                ▼
        一名成员 —— 以下之一：
          · 一个组织              这次协作的一个当事方
          · agent / 自然人        代表某个当事方，或代表自己
          · 外部参与者            （按 §4.4 担保加入）
              每名行动中的成员携带
          · home_org  ：它所属的组织，如果有
          · capacity  ：它在这里代表那个组织，还是代表自己
```

**图的说明：**

- **`Organization` 是唯一拥有权威的节点。** Admin、Policies、Agents 挂在它下面，是因为它们**从它取得资格**，不是因为它们是它的组成部分。
- **组织是一种成员。** 一个横跨三个组织的 Group 有**三个组织成员**，行动中的成员 `home_org` 指向它们。
- **⇒ 同一个组织因此同时出现在两个平面上，是两个不同的东西。** 在治理平面上它是**治理域**（它的 Admin、Policies、Agents）；在协作平面上它是**当事方**（Group 其他参与者之一）。**这是同一个对象的两个视角**：治理平面与协作平面彼此平行，Group 也不持有任何组织的内部。把它当作包含关系，会**合并掉 §2 原则 8 分开的那两个边界**。
- **一个 Group 有没有组织成员，是条件性的。** **组织内 Group** 没有，其成员的 `home_org` 指向 `controller`；**跨组织 Group** 中，凡自己作为当事方承担责任的，每一个当事方对应一个组织成员。第二种情形何时成为必需，由跨组织 Profile 规定（`group-collaboration.md` §14）。
- **一个组织是「参与者」还是「层」，是资格问题。** 一个出现在 Group 与成员之间的组织，**若它自己有登记、准入、状态、可移除**（`group-collaboration.md` §14.1 P1），它就是**参与者**；否则才是**层**。这个差别不是措辞：**层**会把治理边界嵌套进协作边界，并让一个**代表自己**行事的成员在 Group 内无处立足；**参与者**则两者都能表达。
- **`Delegation` 横向走**（Admin 与 Agents 之间）。**授权关系不是汇报线。**
- **`Membership / Role` 是唯一跨平面的边。** 准入就是核对成员的 `home_org`、以及沿它回溯的那条权限链的地方；那条链是 `organization-governance.md` §4 的题目，核对本身在 `group-collaboration.md` §4。
- **`Principal / Controller` 在 Organization 之上**，因为「谁可以代表这个组织」必须终止于某处。

## 4. 三个层面

| 层面 | 它的主体 | 它拥有的问题 | 由谁规范 |
|---|---|---|---|
| **Organization** | 治理域——谁可以代表一个主体行事，到什么时候为止 | *谁有资格授权这件事？* | `organization-governance.md` |
| **Group** | 协作域——来自不同域的各方如何一起工作 | *在什么上下文里，代表谁，一起做事？* | `group-collaboration.md` |
| **Federation** | 注册表之间的空间 | *验证方如何到达一个不由自己的 Registry 持有的记录？* | `group-collaboration.md` §9 |

**三个层面彼此并列。** Organization 不包含 Group，Group 不包含 Federation。**两个组织可以在没有联邦的情况下协作**：联邦是 **Federation 层面**的可选基础设施，**不是 Group 层面的前置条件**。**由此，对应的分册之间是并列，而不是层级。**

## 5. 权威从哪来

每套实现都必须能走完的一条权威链的形状：

```
① 设立依据  ──▶  ② 职位  ──▶  ③ 任职者  ──▶  ④ 根权威依据
 凭什么存在        有哪些角色      谁在任、何时        最初那份权从哪来
```

**④ 是链条的终点**：「谁授权了这件事」在这里得到第三方能核对的答案。**任一层断裂即整条链不成立**——这正是它要被回溯、而不是被断言的原因。

**本文档留给分册的**：起点是否需要外部签发者（不需要）、章程可以是什么形态、超过一个 controller 时的阈值如何满足、满足不了时怎么办。那些是 `organization-governance.md` §4、§12.1、§12.2。

## 6. 身份：哪些对象需要 DID

把原则 2 用在 §3 的模型上：

| 对象 | DID | 为什么 |
|---|---|---|
| **Principal / Controller** | 可以有 | 它是权威的终止主体；它是否需要自己的可验证身份，取决于它是否跨域行动 |
| **Organization** | **可跨域寻址时** | 它**始终**有可识别的身份上下文；DID 使该上下文**可被非其成员的一方验证**。见 `group-collaboration.md` §4.5 |
| **Administrator / Representative** | **跨域行动时** | 它执行治理动作，必须可为这些动作归因。它**不是**一种特殊的 DID 类型——它是 **DID + Role + Delegation**。**原则 2 对 Administrator 的适用，与对组织、对 agent 一样** |
| **agent** | **跨域时** | 在本地它只需要可识别的上下文；跨域才把它升级 |
| **Group** | 可选，视模型而定 | Group 可以拥有独立的治理身份；模型里没有任何一处要求它有 |

**这张表就是那条原则的表格形态**，也是「身份」与「DID」在本族内**从不同义**的原因。

## 7. 对核心的设计约束

这些是**没有任何单个分册拥有的**约束，因为每一条都是**整个模型**的性质。写在这里，是为了让任何一份分册都不能悄悄把它关死。

| # | 约束 | 为什么它是约束而不是功能 |
|---|---|---|
| **C1** | **核心数据模型必须保持联邦的可能。** 联邦可以不实现——MVP 可以只跑一套 Registry——但**没有任何字段、标识符或解析规则可以使第二套 Registry 无法加入** | 这是**对核心的设计约束**，不是核心的功能。一个将来无法联邦的核心，**加一层联邦也修不好** |
| **C2** | **agent 在本地身份上运行** | 原则 1。若运行即需要 DID，模型就等于给每一次本地使用强加一次全球注册 |
| **C3** | **跨域信任建立在验证方自己的解析器配置之上** | 原则 9。验证方**自己配置的解析器**才是信任锚，主体的 Registry 不是 |
| **C4** | **一条记录必须仅凭记录本身与公开材料即可被验证** | 只有在某个运营方在线时才能确立其真伪的记录，**不是证据** |
| **C5** | **两方之间的每一条边界都必须能双边表达** | 协作与联邦都是**双边**的；引入一个强制中介，就是把模型去掉的那个中心又装回来 |

**C1 与 C3 合起来，就是联邦够用判据所测的东西。** 这条判据属于本层，因为没有哪一份分册能单独给出它：

> **两个互不隶属的 Registry 之间，任一方都不需要改自己的实现，就能让对端的验证方完成一次完整的身份验证与状态检查。**

这是一条**测试**，不是一段描述。若答案要求一个没人采用的共享 schema、一份事先签署的双边协议、或任何一方改实现，**它就不通过**。

## 8. 治理事件与证据

治理动作——注册、授权、加入/退出组织、加入/退出 Group、任务委派、任务结果、撤销——**应当能够**形成证据。它们是否**必须**、以什么格式，是 `organization-governance.md` §8 与 `evidence-record.md` 的事。

**本层贡献的是这条要求的形状**，不是它的内容：审计与治理数据**与实时 Runtime 状态分开存放**——使审计不依赖运行中的系统，也使系统下线不会把记录一起带走。那正是 §7 的 **C4**。

## 9. 本架构舍弃的前提

**本节为什么存在**：明知有相近工作而仍然写，就有义务**说出舍弃了哪些前提**。**说前提而不说文档，是有意的**——前提是关于**一类做法**的主张，任何人都能拿它对照自己知道的系统；而**文档引用会过期**。至于「**哪些**文档持有**哪条**前提、什么版本、什么状态」，那是一次**调研**，属于协议族架构的**生态矩阵**，不属于本层。**不点任何对象，也正是本族体例约定（`overview.md` §5）里“记录状态”那条义务在此处不被触发的原因。**

| # | 前提 | 它在哪一类做法里通行 | 若被悄悄引入，会破坏什么 |
|---|---|---|---|
| **D1** | **权威由签发者产生**——授权链起始于一个**先于该组织存在**的实体 | 机构治理模型 | §5 的第④层。一个**自我设立的组织**将没有可核验的起点，「谁授权了这件事」也就没有**不依赖外部**就能得到的答案 |
| **D2** | **互认必须先有一份协议**——两方只有在条约、公开信任列表或符合性要求之后才能互相依赖 | 联邦模型 | 协作将**需要先签条约才能开始**；联邦会从可选基础设施变成**协作层的前置条件**；C5 不成立 |
| **D3** | **签发身份的注册表就是信任根**——身份与持有它的那套部署不可分离 | 注册表中介的身份体系，**包括与本架构最接近的那些** | 迁移变得不可能；「运营方自己的注册表能解析该记录」成为跨域信任的前提——**C1 与 C3 双双不成立** |
| **D4** | **保证度等于同意者的数量**——高等级意味着多个 authority 联签 | 信任凭证体系 | 单一运营方的部署**会被封在最高等级之下**；而等级会变成「有多少人同意」，而不是「核验了什么」。**本架构的等级由已注册的元数据算出，而「接受哪些等级」留给验证方自己的策略** |
| **D5** | **记录的真伪只在其签发方系统在线时成立** | 多数运营系统 | 证据将不再是证据。**C4 的存在就是为了让它不是** |

**在单一凭证体系内定义的联邦层，不延伸到另一个体系。** 这样的层级关联的是共享 proof 格式与 authority 模型的 authority 之间；它对**另一套体系**的等级**不确立任何东西**。**本架构转而从验证方自己的配置推导跨体系信任**，因为一个不属于任何一方的验证方，没有可承认的 authority。
