# 生态矩阵

**外部件登记：本族依赖谁、依赖到什么程度、依据是什么**

> 状态：草案（v0.1）｜ 日期：2026-10-10 ｜ 层：L7 方法
> 定位：Vision §15 的**数据来源**。§15 只给「对象是什么 + 与它的关系」；本件补齐证据列
> 原则：**一条不写清证据的名字，不算一条**
> 相关：`chasi-vision` §5（互补）· §10（五种处置）· §15 · `protocol-suite-architecture.md` §6 与 §14

---

## 1. 本件解决什么

Vision §5 说「**互补**——只补既有生态在跨组织身份、授权、治理、证据、问责上的空白」，并注明「**尚无判据**：要定它，需先能列出哪些能力已成熟」。

**本件就是那张清单。** 有了它，「互补」从一句表态变成一条可判定的要求：**对每一个对象，本族只做它没有覆盖的部分**——它覆盖了什么，看「采纳证据」列。

**本件也是 §5 三种态度（兼容／互补／独立）里唯一尚无判据的那一种的数据支撑。** 兼容的形式在 `assembly.md` §3，独立的形式另有待定（见 §6）。

## 2. 体例

| 列 | 怎么读 |
|---|---|
| **对象** | 只写全族通行的名字，不写产品名 |
| **版本 / 日期** | 取自对象自身的公开信息；**拿不到就写「——」**，不写「未知」充数 |
| **策略** | 用 `protocol-suite-architecture.md` §5 的**五种处置**：采用 · 映射 · 剖面扩展 · 适配 · 自定义。「研究」「跟踪」是不采取处置时的观察档位 |
| **采纳证据** | **仓内何处引用了它、引到什么程度。** 这一列是本件的主列——其余各列都是它的说明 |
| **许可** | 对象的授权方式。**未取到一手来源的一律写「未核」** |
| **状态** | 机构性 · 个人稿 · 社区项目 |
| **复查条件** | **不是「什么时候复查」，而是「出现什么条件时必须复查」**——与 `chasi-vision` §9 对「记」的要求同一体例 |

**为什么是「复查条件」而不是「复查日期」：** 日期会过期而无人察觉；条件不会——条件一旦成立，读者自己就知道这条登记已经旧了。

## 6. 已知缺口

**本件现在能支撑「互补」的判定，但有三处不够。**

1. **许可列 16 项里只有 2 项经一手核实**（A2A、MCP，2026-10-10 取自各自仓的 LICENSE）；**12 项标「未核」**（其中 2 项是「自述，未核」），**2 项是个人稿、标「个体稿」**——**标「未核」不是省略，是这条登记本身还不完整。** 要补齐，需逐个取一手许可文件。
2. **两项状态未定**：AAIF（是机构还是规范都未明）、NANDA（未给对象形态）。**这两条目前只是名字，不构成登记。**
3. **一处来源不一致**：OpenA2A 的 `did:opena2a` 版本号（0.1 与 0.2 两说）。

**另有一处**：本族**自身**（CHA2A 协议体系 · CHASI）不出现在本表——它们不是「现有生态」。两者的关系在 `chasi-vision` §14。

---

## 7. 本件不做什么

- **不做许可合规结论**——本件记录「许可是什么」，**判断「能不能这样用」是另一件工作**；
- **不替 `chasi-vision` §15 规定「关系」**——那一列在 §15，本件只补证据；
- **不含内部策略判断**——「是否必须纳入跟踪」「与谁最接近」「是否绕不开」属内部件，不入本表；
- **不收录本族自身的件**——那在各层索引表（README）。
