# 组织治理 —— Organization Governance 分册

> 状态：讨论稿（v0.2）
> 日期：2026-10-01
> 定位：本族关于 **Organization 作为主体**的分册——与 `group-collaboration.md`（本仓库），以及 `agent-identity.md`、`evidence-record.md`（身份内核，另一仓库）**并列**——定义权限来源、成员与归属，以及治理动作的留证
> 原则：**能用已有标准就不自造**——权限来源分解为四个可核验的层（设立依据 → 职位 → 任职者 → 根权威依据），由 §4 作为本册自己的回答给出；治理动作的证据引用 `evidence-record.md`。
> **与身份绑定的关系。** 以下规则针对一个**能跨域命名主体的身份绑定**书写；**`did:cha2a` 是工作示例**（实验性草案 v1.1.0，已记入 W3C DID Extensions 注册表），每个字段的写法都使另一个满足 §10 接口点的绑定可以接替它。
> 关联：`group-collaboration.md`（本仓库）· `agent-identity.md` §7（委托与授权范围）· `evidence-record.md`（证据格式）· `overview.md`（族入口）· `did-method-cha2a.md`（所用的身份绑定示例）

## 1. 问题与出路

**问题**：`agent-identity.md` §7 已经定义了「agent 的授权范围由 **controller** 声明」。但**没有任何一处定义 controller 凭什么**。

组织可以注册 DID、可以撤销成员、可以修改策略、可以批准跨组织准入——**这些动作的权限从哪来？** **平台指定管理员，而这个指定本身就是全部权威。** 由此带来三个后果：

1. 权限来源不可回溯——出事时说不清“当初是谁给的权”；
2. 组织换了负责人，旧权限悬空；
3. 成员离开后，它派生出去的授权是否随之失效，没有规则。

**出路**：把 Organization 定义为一个**权限来源可回溯的主体**——不是“平台里的一个条目”，而是**一条能独立验证的授权链的起点**。

**本分册的职责**：
1. 定义 Organization 的对象与字段；
2. 定义**权限的四层来源**（本分册的核心）；
3. 定义成员、角色与归属；
4. 定义治理动作的留证；
5. **引用而不重述**：身份与所用的身份绑定（工作示例中即 `did-method-cha2a.md`）、委托与授权范围的语义（`agent-identity.md` §7）、证据格式（`evidence-record.md`）、协作过程（`group-collaboration.md`）。

## 2. 四层链

**这是本分册对自己那个问题的回答。** 「一个机构的权威从哪来」分解为四层，**每一层都必须可核验**，任一层断裂即整条链不成立。**四层本身与逐层要求见 §4**——本节只固定 §4 不涉及的一件：本册在哪两条前提上与 authority-issuer 模型分道。

| | 采用 | 不采用 |
|---|---|---|
| 结构 | ✅ 四层链 | — |
| 前提 | ✅ **接受内部章程作为依据**，起点可以自证 | ❌ 「必须由外部签发者授予」 |

**前提那一行，是本分册与 authority-issuer 模型的分野**：那个模型从一个已经存在的外部签发者出发，本册不要求有这样一个签发者。**这个差异是交付物。** 代价是必须把「起点」本身写清楚（见 §4）。

## 3. Organization 对象

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `org_id` | string | ✔ | 稳定标识 |
| `org_did` | did | **可跨域寻址时需要** | `org_id` 的**跨域升级**，在工作示例的身份绑定下写作 `did:cha2a:org:<id>`。只在自己域内被寻址的组织不需要它；对端如何解析与验证它，见 `group-collaboration.md` §4.5 |
| `charter_ref` | `{hash, uri?, effective_from}` 的列表 | ✔ | **有版本的设立依据**（见 §4 第①层）。至少一条；每条的 `hash` 是校验依据，`uri` 只是定位符。修订**追加**一条，**永不改写已有条目** |
| `controllers[]` | list | ✔ | 谁持有根权限。**至少一个**；多于一个时须说明合成规则 |
| `root_authority_ref` | `{hash, uri?, effective_from}` 的列表 | ✔ | **第④层「根权威依据」的承载**——最初那份权限从哪来。与 `charter_ref` 同形：每版带 `hash`（校验依据）与 `effective_from`；**不得为「平台默认」**（§4 第④层） |
| `roles[]` | list | ✔ | 角色定义：`role_id` · `scope` · `assignable`（见 §6） |
| `members[]` | list | ✔ | 每项：`member_id` · `did` · `kind` · `role_refs[]` · `joined_at` · `status` |
| `policies_ref` | uri \| hash | ✖ | 策略文件引用 |
| `registry_authority` | `{uri, from, to?}` 的列表 | ✔ | 本组织数据由哪个 Registry 承载，**以带时间区间的历史表达**——不是一个当前值。至少一条；最后一条无 `to`。**允许迁移**（与信任根解耦），验证方只需知道「**该 DID 在某段时间由谁承载**」 |
| `status` | enum | ✔ | `active` · `suspended` · `dissolved` |

**够用判据**：一个**不属于本 Organization** 的验证方，只凭上述字段、`charter_ref` 指向的各版本依据、以及各成员的凭证，能独立重建「**谁在什么时候有权代表这个组织做什么**」。

## 4. 权限从哪里来（本分册的核心）

四层来源，**每一层都必须可验证**，任一层断裂即整条链不成立。

| # | 层 | 问什么 | 要求 |
|---|---|---|---|
| **①** | **设立依据** | 这个 Organization 依据什么存在 | 必须指向一份**可核验、有版本的依据**：每个版本带 **hash**（校验依据）与 **`effective_from`**（生效时点），`uri` 可并列但只作定位符。**任命记录它依据的是哪个版本**，验证方因此能回答「**该版本在当时是否生效**」——单哈希证明「哪份文件」，不证明「当时生效的是哪份依据」。**章程的内容是组织自己的事**；本册只要求依据存在、可核验、且有版本 |
| **②** | **职位** | 有哪些角色，各自能做什么 | 角色与权限上下文**分开表达**；**职位是任职者按期担任的岗位** |
| **③** | **任职者** | 谁在担任、何时起止 | 任职是一段**有起止时间的关系**，不是永久属性；任免动作必须留证 |
| **④** | **根权威依据** | 最初那份权限从哪来 | 必须能指向一个**可验证的起点**。**不得是“平台默认”**——平台默认不可验证，等于没有起点 |

层名沿用通行的叫法。

**够用判据（承接 §3）**：验证方能沿四层**独立回溯到起点**，且**不需要联系任何平台**。

> **一处必须写死的**：④ 的起点如果只能由平台提供，那 §3 的够用判据就永远不成立。**这是“可回溯”与“平台断言”的分界。**

**这条判据留给合同与法律的部分**：它回答的是「**该任职者是否有权代表该组织行事**」。它**不**建立「两个组织之间是否互相受约束」。约束力属于合同与法律，在本族之外（见 §12.1 第 5 条）；本册要求的是：一方对另一方代表的**接受**，必须作为一次治理动作留证（§8）——将来要拿出来的，就是这个。

## 5. 成员与归属

### 5.1 成员种类

至少区分三类（与 `group-collaboration.md` §4 的成员模型保持一致）：

| 种类 | 说明 |
|---|---|
| `human` | 自然人成员 |
| `agent` | 组织自有的 agent 成员 |
| `external` | 非本组织成员（跨组织参与者、无 DID 的外部人）——**一律按跨域处理** |

### 5.2 归属的表达

- **本组织的每一名成员都必须显式归属**（`org_id` 不可空）——**在组织之内**，没有归属的成员不存在。**这个范围要紧**：这是关于**组织自身成员资格**的规则，不是关于一切参与者的规则。**Group 的成员可以不带 `home_org`**，那是一个合法情形，有它自己的路径（`group-collaboration.md` §4.4）；
- **“代表谁”必须可区分**：一个 agent 在某个上下文里是**代表 Organization** 还是**代表自己**，必须能判定。二者权限**不合并计算**（详见 `group-collaboration.md` §5.1 第③条）；
- **归属与权限是两件事**：加入组织不自动获得任何角色。

### 5.3 与 `agent-identity.md` §7 的分工

| 分册 | 回答 |
|---|---|
| `agent-identity.md` §7 | **agent 能做什么**（授权范围、scope、委托链） |
| **本分册** | **谁有权去声明它**（Organization 的权限来源、representative 的认定） |

**⇒ 两份各回答一个问题：一份管「被授予的范围」，一份管「授予者的资格」。**

## 6. 角色与不可授予的角色

### 6.1 角色

Organization 可拥有多个角色，例如：管理员 · agent 管理 · 安全 · 群组管理 · 审计。角色与权限上下文分开表达；一个成员可持多个角色（**由持有者各自的 scope 决定，不合并计算**）。

### 6.2 不可授予的角色

**约定：不可授予的角色用「结构性禁止」表达——不参与权值比较、不可被更高权值覆盖，而不是给它一个很大的数值。**

至少应包含两类：

| # | 不可授予 | 说明 |
|---|---|---|
| ① | **根权威本身** | 根权限不可由普通角色授予或取得；变更根权威是一次**显式的重建动作**（见 §7.4） |
| ② | **“给自己授予权限”这一类动作** | 任何角色都不得为自己或自己派生的主体扩权；**包括通过省略字段来扩权** |

> **“字段缺失即视为不允许”**——不写等于没有，不等于无限。这一条与 `group-collaboration.md` §5.1 第①条同一原则。

## 7. 生命周期

原文只处理了“成员离开”一种情形。以下四态按**保守方向**取默认值。

### 7.1 四条连续性规则（先定规则，再定动作）

| # | 规则 | 含义 |
|---|---|---|
| **L1** | **身份连续 ≠ 权威连续** | 身份还在，不等于权限还在 |
| **L2** | **继任者不继承前任的委派树** | 换人即需要重新授权 |
| **L3** | **再授权产生新权威** | 不能靠“引用旧授权”来延长效力 |
| **L4** | **独立链不合并** | 两条互不相关的授权链不得相加出新的权限 |

> **L4 的范围**：它只管**来自不同根**的链。它**不**规定单个根内部如何构成——有几个 controller、用什么阈值（§12.2）。§12.1 里的两处更正，正是这条边界被画过了头。

### 7.2 离职 / 卸任

该任职者的**全部派生授权随之失效**；**不得因为“身份还在”而保留权限**（L1）。历史证据**不删除**——只反映生命周期变化。

### 7.3 继任 / 交接

继任者**不继承**前任的委派树（L2）；需要重新授权（L3）；**交接动作本身必须留证**（§8）。

同一条规则覆盖**吸收**：一个组织被另一个组织吸收时，其任职者在存续方的根之下**重新任命**，而不是被携带过去（§12.1 第 9 条）。

### 7.4 根重建（Re-Rooting）

更换根权威时：

1. **旧根签发的凭证必须显式处置**——作废或换签，二者选一并记录；
2. **不得两套根长期并存而不声明**；
3. 重建动作本身留证，并记录重建理由；
4. **根重建本身就是一次根级动作。** 存在多个 controller 时，它需要达到声明的阈值；阈值不可达时，只能按章程**事先声明**的恢复规则（§12.2）进行。**不得以临时调低阈值的方式执行。**

### 7.5 紧急通道（Break-Glass）

只允许**有时限、有范围、事后必须复核**的越权。

**不得是静默的常设通道。** 判据：一次 Break-Glass 若无法在事后被第三方识别为「这是一次紧急动作」，它就不符合本分册。

三处澄清——这条规则按直接的写法，**恰好在最需要它的地方失效**：

1. **复核者的资格不是「外部」，而是「不是受益人，且有权看到证据」。** 组织内部找不到这样的人时——三个人、一个 controller——**Group 中的对端成员可以充当合法复核者**：但可见性不是自动给的——`group-collaboration.md` §5.3 第③项（**谁能看全量审计**）是 Group 的**声明项**，未声明时按该册的保守默认处理（缺失即视为不允许）。**组织要用上这条路，Group 必须把第③项声明进去**。要求「外部」复核者，会让 Break-Glass 在**最需要它的组织里不可用**。
2. **「未复核」是从链上读出的缺失**，而不是谁来写下的一条记录。 验证方看到一条 Break-Glass 却没有对应的复核记录，就已经发现了它。**不需要任何人写下什么**，这条规则因此不依赖一个可能不存在的执行者。
3. **Break-Glass 下的授权到期即失效、不自动续期**，与是否复核无关。续期走正常授权通道，始终可行。

**未复核的 Break-Glass 必须在状态查询中可见**（工作示例中即 `trust/query`；`group-collaboration.md` §11），使正在决定是否准入的一方看得到。**本册只让它可见，不附评分**；对端怎么处理是对端的事。

### 7.6 解散

1. 凭证**撤销而不删除**，历史证据**保留**——它只记录该组织已解散；
2. **DID 仍可解析并返回 `dissolved`。** 不得变成不可解析：**「已解散」与「查不到」必须仍可区分**，因为验证方的 fail-closed 行为正依赖这个区分。返回 404 的 DID 与从未存在过的 DID **不可区分**，本册不允许这种含糊（§12.1 第 4 条）；
3. 解散动作留证，并记录生效时点。

## 8. 治理动作与留证

以下动作**必须留证**（格式引用 `evidence-record.md`，不另造）：

| 动作 | 至少记录 |
|---|---|
| 注册 / 撤销 agent | 谁 · 何时 · 依据哪个职位 |
| 成员加入 / 退出 | 谁批准的 · 以什么角色 · 起止 |
| 授权 / 撤销授权 | 授给谁 · 范围 · 期限 · 依据 |
| 角色变更 | 前后值 · 批准者 |
| 策略变更 | 前后值 · 版本 · 批准者 |
| 根重建 / 交接 | 依据 · 前后根 · 旧凭证处置 |
| Break-Glass | 触发理由 · 范围 · 时限 · 事后复核结论 |
| **接受另一组织的代表** | 哪位代表 · 代表谁 · 接受的范围 · 核验了哪条依据 · 谁接受的 · 起止 |

**一条硬要求**：审计链**保证据、不保正文**——链上只放最小必要（哈希 + 类型 + 句柄 + 时间），正文可删，**“删正文”本身记为一条审计事件**。

**够用判据**：一条治理动作的证据，**不依赖任何一方的系统可用性**即可被第三方验证其真伪与时效。

## 10. 与已有机制的衔接

| 已有机制 | 衔接点 |
|---|---|
| 身份绑定（工作示例：`did-method-cha2a.md`） | 组织标识（`did:cha2a:org:<id>`）的注册与解析；**它与 Registry Authority 解耦，允许迁移**；`registry_authority` 以**带时间区间的历史**保留，使旧凭证仍能解析到当时的承载方（§12.1 第 7 条）。**对端如何解析与验证一个组织，见 `group-collaboration.md` §4.5** |
| `agent-identity.md` §7 | 委托与授权范围由该分册定义；本分册提供“授予者资格” |
| `evidence-record.md` | §8 的全部治理动作**统一用 Evidence Record 格式** |
| `group-collaboration.md` | 该分册的成员模型与准入三道依赖本分册的“谁能代表组织” |
| 身份绑定的状态查询（工作示例：`did:cha2a` 的 `trust/query`） | 查组织与成员状态；**离线时 fail-closed** |
| `nationalStandardId`（`agent-identity.md` 附录） | 组织若需与区域身份码体系映射，走同一机制 |

**一份密码学实现，服务四处**：身份凭证、治理动作证据、协作记录、卡签名——共用同一套（JWS + JCS 规范化）。

## 11. 参考实现

- 参考 Registry：`https://compliancehub.cn`（见 `README.md`）
- 最小闭环：一个组织 → 依据章程注册 → 指定 controller → 任命两个角色 → 一个 agent 以 `agent` 成员加入 → 一次授权 → 一次撤销 → 全部动作可下钻到证据

**验收判据（不靠形容词）**：
1. 一个**不属于本组织**的验证方，能沿 §4 四层独立回溯到权限起点，**且不联系任何平台**；
2. 四条负路径**必须变红**：改一字节 / 换 kid / 组织域不匹配 / 已撤销；
3. **L1–L4 四条规则各有一条反例测试**（例如：身份仍在但权限应失效；继任者引用前任授权应被拒）。

## 12. 本册固定的，与留给部署方的

本册**没有留待决定的规范要求**。它只划一条线：**协议固定什么，部署方选择什么**。每一条固定项都写出推导依据——**读者可以质疑推导链，而不是只能接受结论。**

### 12.1 本册固定的

| # | 事项 | 本册固定为 | 推导依据 |
|---|---|---|---|
| 1 | 章程的可核验形态 | `charter_ref` 是一份**有版本的依据**：每条带 **hash**（校验依据）与 **`effective_from`**，可选 `uri`（仅定位符），且**每次任命记录它所依据的版本**。单哈希只能证明**哪份文件**，不能证明**作出该任命时生效的是哪份依据** | §4 第①层 + 第④层「平台默认不是起点」 |
| 2 | 多个 controller 时的权限合成 | 根级动作的阈值是**章程声明的参数**。**L4 只管来自不同根的链**；同一个根的 co-controller 就是一个根，k-of-n 签名不构成「合并独立链」。固定三件事：必须声明、**不得由任何单个 controller 满足**、某个 controller 失联**永远不使阈值下降** | L4（范围见 §7.1）+ §7.4 + §12.2 |
| 3 | Break-Glass 由谁复核 | 复核者必须**不是受益人**，且**有权看到证据**；组织内部没有这样的人时，**Group 中的对端成员可以充当**——但那要求该 Group 已按 `group-collaboration.md` §5.3 第③项**声明**其审计可见性（该册默认「缺失即视为不允许」，故不是自动赋予）。授权到期即失效、不自动续期，与是否复核无关。未复核的 Break-Glass **是从链上读出的缺失**，不是一条记录，且必须**在状态查询中可见**——**不打分、不评级** | §7.5 + `group-collaboration.md` §5.3 第③项、§11 |
| 4 | 解散后凭证与证据的处置 | 凭证**撤销而不删除**，历史证据**保留**。DID **仍可解析并返回 `dissolved`**——返回 404 的 DID 与从未存在过的 DID 不可区分，而验证方的 fail-closed 正依赖这个区分 | §7.2 + §7.6 + §8 |
| 5 | 跨组织「组织代表」的承认 | **承认就是 §4 的四层回溯。** 技术上的答案是 §4 的四层回溯；**两个组织之间是否受合同约束在本族之外**。本册要求的是：**一方对另一方代表的接受，必须留证** | §4 够用判据 + §8 |
| 6 | 角色清单的最小公共集 | **角色自定义。** 角色自定义；只有 §6.2 的两类不可授予角色是固定的 | §6.2 结构性禁止 + §4 第④层 |
| 7 | 跨 Registry 迁移的证据连续性 | 连续性来自**证据链而非 Registry**——而这只有在 `registry_authority` 以**带时间区间的历史**保留时才成立，验证方才能知道「该 DID 在某段时间由谁承载」。迁移记录携带**旧承载方 · 新承载方 · 生效时点** | §3 + §8 够用判据 |
| 8 | 章程修订 | 修订 = **追加一个版本**，带自己的 `effective_from`；旧任命依然有效，因为它们的依据是**作出时生效的那个版本**。修订是治理动作，必须留证。若它改变了根权威依据本身，按 §7.4 处理 | §4 第①层 + §7.4 + §8 |
| 9 | 组织合并 | 两种形态都可接受，且**都不合并权限**：**一方存续**——根不变，被吸收方的任职者在其之下**重新任命**（§7.3），被吸收方的旧根凭证按 §7.4 第 1 项处置；或**新设一方**，两个前身各自解散。**一次合并要求每一份凭证都被重签或作废**，否则合并就成了伪造凭证的合法外壳。**法律上的承继在本族之外** | L4（范围见 §7.1）+ §7.3 + §7.4 |

### 12.2 留给部署方的

语义由本册固定，取值由部署方自行选择。

| 参数 | 本册固定的 | 由谁取值 |
|---|---|---|
| 多个 controller 时根级动作的阈值 | 必须**声明**；**不得由任何单个 controller 满足**；某个 controller 失联**永远不使阈值下降** | k 与 n 的取值 |
| **阈值不可达时的恢复规则** | 必须**事先存在于章程中**、**有时延**、**已公布**。临时把阈值调低是攻击，不是补救 | 其形态与时延 |
| 根权威自身触发 Break-Glass 时由谁复核 | 不得是**受益人**，且必须**有权看到证据**；共享 Group 中的对端成员符合 | 章程是否指定一位，或交给 Group |

**同一套机器也管一个有多当事方的 Group。** 指定了多个 controller 的 Group，**复用这张表**，而不是自造一套阈值（`group-collaboration.md` §14.3）——**联盟的联合治理与多 controller 组织的治理是同一个问题，解一次。**

**本册不延后任何东西。** 不覆盖的部分交给具名分册（§9），而不是交给自己的未来版本。
