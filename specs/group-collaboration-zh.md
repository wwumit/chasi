# Group & Collaboration —— 跨组织协作分册

> 状态：讨论稿（v0.2）
> 日期：2026-10-01
> 定位：本族关于**跨组织协作上下文**的分册——与 `organization-governance.md`（本仓库），以及 `agent-identity.md`、`evidence-record.md`（身份内核，另一仓库）**并列**——定义该上下文的对象与规则
> 原则：**能用已有标准就不自造**——任务状态机对齐 A2A Task；证据格式引用 `evidence-record.md`；**骨架是本册自己的**，因为每一个外部群组服务都携带本册拒斥的信任模型（§2）。
> **与身份绑定的关系。** 身份是**引用来的，不是重述的**：以下规则针对一个**能跨域解析主体、并对其状态作答的身份绑定**书写；**`did:cha2a` 是工作示例**（实验性草案 v1.1.0，已记入 W3C DID Extensions 注册表）。§9 说明了本册对一个这样的绑定需要什么，因此另一个满足它的绑定可以接替。
> 关联：`organization-governance.md`（本仓库）· `agent-identity.md` §7（委托与授权范围）· `evidence-record.md`（证据格式）· `overview.md`（族入口）· `did-method-cha2a.md`（所用的身份绑定示例）

## 1. 问题与出路

**问题**：不同 Organization 的 agent 要在一起干活，但**它们不共享同一个信任域**。

**把“谁在这个群里”记在某一方的数据库里，成员资格就不可验证**，跨组织协作的账也只能各记各的。这不是通信能力问题，是**协作上下文缺少可验证的成员资格与记录**。

**出路**：把 **Group 做成一等对象**——成员资格、角色、授权与协作记录都是**可被第三方验证的**，而不是由某一方断言。

**本分册的职责**：
1. 定义 Group 的对象与字段（谁创建、谁在、谁能做什么）；
2. 定义**准入**（不同信任域的成员如何进得来）；
3. 定义**跨组织规则**（权限不放大、撤销级联、责任归属）；
4. **引用而不重述**：身份与所用的身份绑定（工作示例中即 `did:cha2a`）、委托与授权范围（`agent-identity.md` §7）、证据格式（`evidence-record.md`）、任务状态机（A2A Task）。

## 2. 结构从哪来

**复用已有的东西——并把它的信任模型留在原处。**

| 板块 | 从哪来 | 本册补的那一层 |
|---|---|---|
| 身份与地址 | 所用的身份绑定 + `agent-identity.md`，本册不重定义 | 跨信任域的解析 |
| 任务状态机与消息语义 | A2A Task | 接受与结果**带签名**；重定义一处映射（§8） |
| 证据格式 | in-toto / `evidence-record.md` | — |
| **Group 对象 · 成员资格 · 准入** | **协作平面自己的题目。** 身份 · Presence · 群组管理这一分解，是**任何群组服务的通用分解**，本册不主张其中任何一部分是自己的——**但这个通用分解止于单一信任域的边界** | **本册自己的题目**：**跨**信任域的成员资格与准入，以及 §5 的规则 |

**为什么骨架是本册自己的**：现存的群组服务——运营商消息、联邦聊天——各自携带自己的身份与账号模型（电话号码、运营商账号、homeserver 账号），**采用其中任何一个作为骨架，都会把本族要消掉的那种平台断言一并引进来**。它们是**互操作目标**（§11），不是地基。

**顺序说明**：这是 §1 的链条在协作层的落点——身份解析（谁）→ `agent-identity.md`（被授权做什么）→ `organization-governance.md`（谁有资格授权它）→ 本册（在哪个上下文里一起做）。**四环**：一个 Group 接纳的成员，其权限要沿其组织回溯，而那一环属于 `organization-governance.md` §4（四层链）——本册 §4.1 的准入各道都要读它。

## 3. Group 对象

**Group 是一等对象**，不属于任何一方的私有数据库。**它包含的是成员——而成员可以是一个组织。** 每名行动中的成员携带一个 `home_org`；横跨三个组织的 Group 有**三个组织成员**，行动成员的 `home_org` 指向它们（§14）。**组织是成员之中的一个参与者**，而不是成员之上的一层。层会把治理边界嵌套进协作边界，并且会让**代表自己**行事的成员在 Group 内无处立足（§5.1 第③条）；**作为一种成员**，两者都能表达。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `group_id` | string | ✔ | 稳定标识（本分册范围内唯一） |
| `group_did` | did | ✖ | 可扩展；**不是所有 Group 都需要** |
| `controller` | id，**或按 §14.3 为一个集合** | ✔ | 谁对本 Group 的治理负责——可以是 Organization，也可以是任务发起方。**多个当事方持有它，仅在满足 §14.3 条件时成立**，否则 §5.3 第②项将不可确定 |
| `created_by` | id | ✔ | 发起方（与 `controller` 可不同） |
| `members[]` | list | ✔ | 每项：`member_id` · `did?`（按 §4.4 担保加入者可无 DID）· `home_org?` · **`guarantor?`**（担保人标识、担保范围与起止，见 §4.4）· `joined_at` · `status` |
| `roles[]` | list | ✔ | 角色**不附着于** Organization 成员资格 |
| `policies` | 内嵌 object，**或带 `hash` 与 `effective_from` 的规则版本引用**（`naming.md` §2.2） | ✔ | 至少含：准入档位 · **谁同意才算准入（§4.3）** · **谁能看全量审计（§5.3 第③项）** · **可见性（§5.3 第④项）** · 谁能解散 · **账本位置与不一致裁决规则（§5.3）**。群组规则是**规则版本**，引用须指向**作出时生效的那一版** |
| `capabilities[]` | list | ✖ | 可与 Presence 结合（§7） |
| `endpoints[]` | list | ✖ | 发现入口 |
| `status` | enum | ✔ | 见 §6 九态 |

**够用判据**：一个**不属于本 Group 创建方**的验证方，只凭上述字段与各成员自己持有的凭证，能独立重建「**谁在什么时候以什么身份在这个 Group 里**」。

## 4. 成员资格与准入

**成员资格必须可验证。**

### 4.1 准入三道（缺一不可）

| # | 要求 | 说明 |
|---|---|---|
| ① | **身份可验证** | 至少达到可核验档；**不接受仅声明**（对照工作示例身份绑定的 L0–L4 档，`did-method-cha2a.md`） |
| ② | **双方各自确认** | 邀请方确认邀请；被邀方管理员确认其成员加入。**信任需要各自确认**——A 确认过 ≠ B 认 |
| ③ | **席位与范围** | 该成员在本 Group 内的权限上下文，**与它在自己 Organization 内的角色分开表达** |

### 4.2 加入时应当记录的

每个成员加入时留下一条可验证记录：`who`（DID）· `by_whom`（谁批准的）· `accepted_by`（**哪一方**接受其进入本 Group，在哪一侧）· `at`（何时）· `as_what`（以什么身份/角色）· `home_org`。

> **`accepted_by` 是将来被问到时真正要拿出来的那个字段。** 一条核验通过的授权链说明该成员**可以**代表其组织；它本身**不**说明对方**同意在此受约束**。两个组织之间是否受合同约束在本族之外（见 `organization-governance.md` §12.1 第 5 条）；本族要求的是：这次接受**在记录里**。

### 4.3 谁同意才算准入

**默认是两次确认**——邀请方的，以及该成员所属组织的（第②道）。**默认不要求第三方批准**，因为第①道的独立可核验**本身就是**第三方信任的替代品。

**但 Group 可以要求更多，而且必须说得出来。** 因此 `policies` 要指明「**准入需要谁的同意**」：仅邀请方 / 邀请方加所属组织 / 再加全体现有成员 / 或一个声明的法定数。**这是声明项，不是固定规则**——一个要求全员同意的联盟能够表达出来，不在意的 Group 沿用默认。

### 4.4 担保加入的参与者

**没有归属组织**、或**没有 DID** 的参与者，在第②道下**没有第二个确认者**。这类参与者仍可加入，但**只能在一个具名担保人名下**——由一名成员为其担保，并因此承担对它的可追责性。

- **担保是一次治理动作，必须留证**：谁担保 · 担保谁 · 什么范围 · 起止。
- **准入需要担保人。** 第①道**永不豁免**：一个不可核验的参与者之所以能进来，是因为**有一个可核验的当事方站在它背后**，而不是因为要求被搁置了。
- **担保随担保人终止。** 担保人被移除或离职，被担保参与者的席位随之结束。

### 4.5 组织的跨域标识

**组织始终有可识别的身份上下文；当它需要被对端验证时，才升级出 DID。** 这是架构层的 `Identity ≠ DID` 原则用在 Organization 上：

| | |
|---|---|
| `org_id` | **恒有**——组织自己的稳定标识，在其自身域内有意义 |
| **所用的身份绑定下的组织标识**（工作示例：**`did:cha2a:org:<id>`**） | **跨域升级**——使该组织可被**非其成员**的一方解析与验证的那个东西 |

**准入方按顺序检查：**

1. **标识能解析**——通过**准入方自己配置的**解析器（工作示例中即 `did-method-cha2a.md` §4.1）。**任何一方都不会被要求相信某组织对自身身份的说法**；
2. **状态是新的**——该组织的注册表作答，否则按类别 fail-closed 拒绝准入（§5.2）；
3. **权限能回溯**——链条回到该组织的章程依据；那是 `organization-governance.md` §4 的题目，不是本册的。

**只在自己域内被寻址的组织，仅以 `org_id` 标识。** DID 出现在边界上，而这一节就是它的用途。

## 5. 跨组织规则（本分册的核心）

### 5.1 权限不放大

**下游权限不得大于上游授予范围。**

三处必须强制：

| # | 处 | 要求 |
|---|---|---|
| ① | **委派时** | 不得扩大上游授予的范围（scope / 目标 / 期限）。**字段缺失不等于无限制**——缺失即按不允许处理 |
| ② | **Group 角色** | Group 内的角色**不得扩及** Organization 内的权限 |
| ③ | **两种身份** | 权限是**分离，不是交集**：以某个身份行动就用该身份的 scope，以另一个身份行动就用另一个的，**二者永不相加**。一个 agent 不能靠叠加取得任一方都没有的权限——**但也不额外收缩**：要求两者**取交集**，是用一条本册从未推出过的规则去缩小权限，而且会让双身份代表**不可用**。**每一次行动都必须指明用的是哪个席位** |

> 第③条是本分册与“同组织多 agent”的关键区别：在同一个信任域里，权限叠加是自然的；**跨域时，叠加就是越权**。

### 5.2 撤销的级联，以及状态必须有多新

任一方撤销某成员的授权后：

1. 该成员在 Group 内的**相应权限必须级联失效**；
2. 撤销动作本身必须留证据（引用 `evidence-record.md`）；
3. **状态必须有多新，按「这个判断要做什么」分级**，而不是一个全局数字。原来写的是单一「最大可容忍延迟」，它**与 §11冲突**：如果 Registry 不可达即 fail-closed，那么「容忍陈旧状态」的窗口**永远不会打开**——状态根本读不到。**两条规则是互斥的，不是互补的。**

| 判断类别 | 对新鲜度的要求 |
|---|---|
| **改变权威的判断**——准入 · 授权 · 解散 · 让一次撤销生效 | **必须基于新鲜状态；不可达即拒绝。没有时间窗口** |
| **只读判断**——展示 · 审计 · 报告 | 可以带一个**声明的陈旧上限**；但该判断**必须记录它所依据的状态时点** |

**第二行带出一条硬要求**：任何依据陈旧状态作出的判断，**必须把该状态的时点写进记录**，否则事后无法复核。

### 5.3 责任归属（跨组织协作的定义性特征）

跨组织协作出事时，必须能**唯一确定**四件事：

| # | 问题 |
|---|---|
| ① | **协作记录在哪本账上**（谁的存储、谁的哈希链） |
| ② | **谁有权解散** |
| ③ | **谁能看全量审计** |
| ④ | **谁不能看** |

**这四项不确定，跨组织协作就没有可追责性**——而可追责性正是它与“平台内多 agent 群聊”的真正区别。

**四项都由 Group 声明。本册固定的是“未声明时”的保守默认：**

1. **各方持有自己产生的、以及被显式指向自己的部分。** 要跨过去的，**必须声明**。可见性与 §5.1 第①条同一纪律：**缺失即视为不允许**——管权限的那条规则，同样管暴露。
2. **没有默认的权威账本。** Group 必须事先声明：**(a) 两本账不一致如何被检出**，**(b) 裁决规则**。**任何一方都不得是真相的唯一作者**——指定某一方为准，等于把“平台断言”从平台搬到 Group，而这一族存在的理由就是消掉它。
3. **记录存活于 Group。** 解散**不**要求任一方删除自己持有的副本（见 `organization-governance.md` §8「保证据、不保正文」）。
4. **权限被撤销之后，历史仍然成立。** 一个成员在被移除之前合法看到的东西，**不因移除而在事后变得不可见**。「谁不能看」（第④项）因此必须是**在某个时点上可确定**的事实，而不是一个**会回溯变化**的量——否则它无法核验。**内容（与协作记录相对）不是本册的题目**：把某一方的可见副本下线，是部署方的内容与数据保护义务，本册只要求下线动作**记为审计事件**。

## 6. Group 生命周期

```
CREATE → INVITE → JOIN → VERIFY → ACTIVE → ROLE CHANGE → LEAVE / REMOVE → REVOKE → CLOSE
```

九态之上补三条要求：

1. **每一态都可观测、可留证**——不得发明只存在于某一方内部的状态；
2. **非终态都可取消**，且取消是**业务迁移、可再迁移**；它与“拒绝”不是同一件事（拒绝是对同一次校验的判定，必须单调）；
3. **CLOSE 不得留下悬挂任务**——未终结的任务必须显式取消并记录。

## 7. Presence 的 Agent-native 化

不仅表示 `online` / `offline`，还可表达 `available` · `busy` · `working` · `accepting_tasks` 等状态；可与 Capability Discovery 结合，为任务协调提供实时上下文。

**边界：Presence 不产生任何权限。**「在线」与「可被派单」是两件事。

## 8. Chat 与 Task 的关系

**Chat 是 Group 的一种 communication mode；Task Collaboration 是另一种 coordination mode。** 二者共享 Identity、Membership、Signature、Policy、Evidence 等底层机制——**二者共用一个协议**。

**一处必须重定义**：A2A 的 `TASK_STATE_COMPLETED` 只是**执行方自我宣告**，没有“待验收”。本分册在语义上把对端的 `COMPLETED` 映射为**待验收**；对端的 `REJECTED`（服务方拒接）与本方的“驳回”（验收不通过）**同名不同义，必须改名区分**。

## 9. 跨 Registry 的解析与验证

**所用的身份绑定已经判掉了这件事**，而它判定的东西很窄。

### 9.1 四个问题最终都落在同一个动作上

§1 的四个问题，每一个都终止于「**解析标识、读它的状态**」：

| 问题 | 它需要注册表提供什么 |
|---|---|
| 它是谁 | DID Document |
| 谁授权它 | 该组织的状态，以及其章程依据的**版本** |
| 它在什么上下文里行动 | 该成员在 Group 内的状态 |
| 它做过什么 | 记录**作者**的状态 |

### 9.2 身份绑定已定

- **DID 命名一条记录，不命名一个位置**（工作示例中即 `did-method-cha2a.md` §4.1——与 `did:key` 同理）：只给一个 DID，验证方推导不出哪套部署持有该记录。
- **验证方自己配置的解析器，就是它所返回文档的信任锚**；且**联邦之下信任语义保持不变**。
- **联邦部署不得被假定信任或转发给任何其他注册表，除非被显式配置为如此。**
- 关于「承认」本身：**一方是否承认另一方的签发，是各方的本地策略。**

**⇒ 这里没有任何一处要求两个 Registry 就任何事达成一致。** 验证方能到达对端的 Registry，是因为**它自己的运营方配置了它**。所以跨 Registry 验证只需要三样东西，而这三样本族都已固定：**解析**（发现）· **一个状态回答**（工作示例中即 `trust/query`）· **§5.2 的新鲜度规则**——加上 Registry 不可达时按判断类别分级的 fail-closed（§5.2）。

### 9.3 不需要互认

**联邦机制存在，是为了解决一个问题：让一个 authority 的断言能被另一个接受。** 联签阈值、公开信任列表、带信任等级映射的协议、authority 之间推送撤销——**它们各自都预设了：一方在某种安排使其可接受之前，不能依赖一个外来断言。**

**在单一凭证体系内定义的联邦层，不延伸到另一个体系。** 这样的层级关联的是共享 proof 格式与 authority 模型的 authority 之间，对**另一套体系**的等级**不确立任何东西**。**本册为何去弃上述前提、以及架构层为何说前提而不点文档名，见 `governance-architecture.md` §9。**

**本族的核心主张是把这个问题消掉，而不是解掉它。** 一个不属于任何一方的验证方**没有需要承认的 authority**——它读 DID Document、状态和签名，然后自己判断。

**剩下的事是一个商业决定。** 真正悬着的是「**验证方选择配置哪些 Registry**」，那是每个运营方替自己做的一个商业决定。**协议替不了他们做**；写一个协议只会把这个决定挪到一个更不可问责的地方。

### 9.4 多 Registry 解析器的最小能力集

联邦语义已在 §9.2 判掉。**这里尚待构建的是一个被配置为查询多套部署的解析器，它的操作面**；其最小能力集是：

Registry discovery · DID resolution hint · Passport retrieval · credential verification · status checking。

**先例，以及前提差异。** 「无 DNS 锚点的发布方如何被解析」这一问题，已由 `draft-raskar-agentic-web-federated-resolution-01` 定义——*Registry-Assisted Discovery for AI Agents and Workloads Without DNS Discovery Anchors*，Informational 个人稿，2026-07-20，Raskar · Sharaf · Chari，无 IETF 背书、无正式地位。它定义了决议记录、AI Catalog 信封、Authority Evidence、实验性 HTTPS 绑定、缓存与撤销，以及媒体类型 `application/agent-resolution-target+json`。其中两条与本册的规则一致：

| 它的规则 | 本册在同一处也有 |
|---|---|
| 客户端通过本地配置或部署策略选择 Registry（其 §9.3） | §9.2——验证方自己配置的解析器是信任锚 |
| 仅在 Registry 中存在，并不使一条绑定成为权威；解析器应知道自己得到了哪种校验（其 §10.9） | §9.3——一个不属于任何一方的验证方，没有可承认的 authority |

三处前提不同，而差异正是 §9.2 的依据：

| | 该草案 | 本册 |
|---|---|---|
| **解析由什么驱动** | **规模**——没有可用 DNS 锚点的发布方：小微企业、个人、托管工作负载 | **信任边界**——一个不属于任何一方的验证方，需要读到由**不是它自己的** Registry 持有的记录 |
| **Registry 之间的互操作** | **推迟**：该草案把目录联邦、全局交换台行为、通用目录转介与目录间路由移出范围，其附录 C 把 Registry 互操作留给一份可能的未来文档 | **已判**：承认是各方的本地策略，不需要互认（§9.3），因此 Registry 之间没有需要补的缺口 |
| **解析器需要被告知什么** | 某个身份该用哪种发现机制 | 它会接受哪些 authority（C3，`governance-architecture.md` §7） |

同一组人的一份同期刊印本——*A Global Switchboard for the Agentic Web: Connecting Discovery Islands Across Enterprises, SMBs, and Individuals*，MIT Media Lab，v0.1，2026-07-20，标注 *Request for Comments*——提出的是更宽的「目录的目录」模型。该草案把它引为背景，并声明目录间功能不在其修订版范围内。该草案附录 C 列出的三个开放问题，在本族已有回答：**跨身份类别的 authority 证据的统一凭证格式**（`evidence-record.md`）、**透明日志与可审计的恢复程序**（`organization-governance.md` §7 与 §12）、**各自选择 Registry 的运营治理**（本册 §5）。

## 12. 参考实现

- 参考 Registry：`https://compliancehub.cn`——所用身份绑定的参考部署
- 最小闭环：两个不同 Organization 的 agent → 创建 Group → 准入三道 → 签名消息 → 创建并分配 Task → 签名结果 → Evidence

**验收判据（不靠形容词）**：
1. 一个**不属于本 Group 创建方**的验证方，能独立重建成员与协作记录；
2. 四条负路径**必须变红**：改一字节 / 换 kid / 成员域不匹配 / 已撤销；
3. **包含至少一个外部第二方**——全部在自己内部完成的闭环只能算测试夹具，**验证不了“不共享同一信任域”这一核心主张**。

## 13. 本册固定的，与留给部署方的

本册**没有留待决定的规范要求**。它只划一条线：**协议固定什么，部署方选择什么**。每一条固定项都写出推导依据——**读者可以质疑推导链，而不是只能接受结论。**

### 13.1 本册固定的

| # | 事项 | 本册固定为 | 推导依据 |
|---|---|---|---|
| 1 | 准入需要几方批准 | **默认两次确认**——邀请方的，以及该成员所属组织的；第①道的独立可核验就是第三方批准者的替代品。`policies` 指明**准入需要谁的同意**（§4.3），因此要求全员或法定数同意的 Group 说得出来 | §4.1 第①、②道 + §4.3 |
| 2 | 协作记录的归属 | **各方持有自己产生的、以及被指向自己的部分**；多跨的部分必须声明——与 §5.1 第①条同一纪律（缺失即不允许）。**没有默认的权威账本**：不一致如何检出、如何裁决由 Group 声明，因为**任何一方都不得是真相的唯一作者** | §5.3 + §5.1 第①条 |
| 3 | 成员可见副本的下线 | **内容**不是本册的题目——是部署方的内容与数据保护义务，下线动作记为审计事件。**证据**是本册的题目：记录存活，且**撤销权限不等于撤回历史可见性**——成员在被移除前合法看到的东西，事后不会变得不可见 | §5.3 + §10 + `organization-governance.md` §8 |
| 4 | 未终结任务在 CLOSE 时的取消语义 | 映射到 A2A 的 **cancelled** 态 | §6 第 3 条 + §2 |
| 5 | Presence 的最小取值集 | `online` · `offline` · `available` · `busy` · `working` · `accepting_tasks`——默认集 | §7 |
| 6 | 双重代表——一个 agent 同时代表两个组织 | **分离，不是交集**：两个席位，各用各的 scope，**永不相加**。§5.1 第③条禁止两种身份的**并集**，从未要求**交集**——交集是用一条本册推不出来的规则缩小权限，会让双身份代表不可用。**每次行动必须指明用的是哪个席位** | §5.1 第③条 + §4.1 第③道 |
| 7 | 跨 Registry 的撤销传播 | **新鲜度按判断做什么分级。** 改变权威的判断基于**新鲜状态、无窗口**；只读判断可用**声明的陈旧上限**，且必须记录所依据的状态时点。单一全局容忍值与 §11 无法调和——那里 Registry 不可达即 fail-closed | §5.2 + §11 |

### 13.2 留给部署方的

| 参数 | 本册固定的 | 由谁取值 |
|---|---|---|
| **只读判断的陈旧上限** | 必须**在 Group 对象中声明**，且在其下作出的每个判断都**必须记录所依据的状态时点**。它**不适用于**任何改变权威的判断——那类判断要求新鲜状态、无窗口（§5.2） | 取值——需真实第二方实测；成员跨法域的 Group 可能需要不止一个 |

**本册不延后任何东西。** 本册之外的部分交给具名分册（§10）。**唯一的可选扩展是 §14**——那是 profile，不是延后：基线在没有它的情况下照跑。

## 14. 跨组织 Profile（企业级）

**可选。** 本册的基线覆盖的是「当事方只为自己的成员**背书**」的协作。本 Profile 面向的是**组织本身即为当事方**的协作——**长期安排，而不是单次委派**。只跑组织内 Group、或只跑组织间一次性任务的部署，不需要它。

**它只使用已有的核心对象。** 下面每一条，都是本册已有规则**升一级使用**。

### 14.1 六条要求

| # | 要求 | 复用的 |
|---|---|---|
| **P1** | 当事方**注册为本 Group 的一个成员**，其 DID 解析为 `org` 资源 | §3 `members[]` |
| **P2** | 代表某当事方的成员，其 `home_org` 指向它；且**当事方先于其成员注册** | §3 `home_org` |
| **P3** | 当事方走**同样的三道准入门**（§4.1），由它自己的管理员确认 | §4.1，升一级 |
| **P4** | 当事方被移除或退出，**级联**到所有 `home_org` 指向它的成员 | §5.2，升一级 |
| **P5** | 成员可另持一个**独立席位**——「在本 Group 内代表自己」就是这么表达的 | §13.1 第⑥项 |
| **P6** | `policies` 声明**当事方的准入需要谁同意** | §4.3，升一级 |

**P2 是要求。** 第②道门要求被邀方管理员确认。**若该组织还不是参与方，那就等于让一个管理员执行参与方的动作、却不持有参与方的资格**——本 Profile 存在的意义就是消掉这个错位。

### 14.2 成员的 `home_org` 与本 Group 的三种关系

| | `home_org` 指向 | 含义 | 谁对该成员负责 |
|---|---|---|---|
| **①** | **本 Group 的一个当事方** | 本 Profile 下的常态 | 该当事方 |
| **②** | **一个不是当事方的组织** | 该组织为成员背书，但自己不加入这次协作 | 该组织 |
| **③** | 空 | 成员代表自己，或按 §4.4 加入 | 担保人（§4.4），或成员自己 |

**把 ① 与 ② 分开，才使「谁负责」可确定**：成员所属的组织被点出来了，但它在 Group 内的**资格**没有——§5.3 的四项就答不全。

### 14.3 多个当事方

一个 Group **只有在适用与 `organization-governance.md` §12.2 相同的阈值与恢复机制时**，才可指定**多个 `controller`**：阈值必须声明、不得由任何单个当事方满足、某个当事方失联时不下降，且恢复规则必须**事先存在、有时延、已公布**。不满足这些条件而指定多个 controller 的 Group，**不满足 §5.3 第②项**——因为「**谁有权解散**」将不可确定。
