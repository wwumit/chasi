## 1. 核心主张

> **一个不属于任何一方的验证方，应当能独立回答四个问题——**
> **它是谁 · 谁授权它 · 它在什么上下文里行动 · 它做过什么**——
> **不必去问被验证的那一方，也不必成为任何人的客户。**

**这一句定义的是核心**：四个问题覆盖不到的，不属于核心（其余部分落在哪里，见 §4）。

**「不联系任何平台」的准确含义是：不去问被验证的那一方。** 它不表示验证方离线。它会去读一个注册表——但**是它自己配置的那个**，而该注册表所返回的文档，其信任锚就是它（`did-method-cha2a.md` §4.1），**不是被验证方的服务**。这个差别是实质性的：「**我能信这个吗**」由**验证方自己的配置与自己的阅读**回答，**永远不由被验证方的说法回答**。

**它成立需四个条件同时满足**（各分册分别承担）：

| 条件 | 由谁承担 |
|---|---|
| 身份可解析，且信任根可迁移 | 解析：`did-method-cha2a.md`；迁移：`governance-architecture.md` 原则 9 ＋ `organization-governance.md` 的 `registry_authority` |
| 授权者的资格可回溯 | `organization-governance.md` |
| 跨信任域的协作上下文可验证 | `group-collaboration.md` |
| 做过什么可被第三方独立验证 | `evidence-record.md` |

## 2. 本族解决什么问题

**问题**：agent 生态里，身份、证据、协作各有标准，但**每一家都止步于单一信任域的边界**。

具体表现：

- 身份的信任根绑在某一家的注册表上，换不掉；
- “谁在这个群里”记在某一方的数据库里，不可验证；
- 组织能发权限、能撤成员，但**权限最初从哪来**没有可回溯的答案；
- 验证记录由某一方自持，出争议时无法独立复核。

**出路**：不改变各方的信任根，而是让**跨信任域的判断**成为可能。

**本族是增量。** 不与任何既有的身份、证据或协作标准竞争，也不取代任何一方的实现；本族补的是它们都没有的那一层。

## 3. 族内文档

```
身份内核仓库（`did-method-cha2a`）—— 身份与证据的规范性内核：

  did-method-cha2a.md          主规范 · 唯一承载规范性要求的文档
  agent-identity.md            agent 主体
  evidence-record.md           做过什么的记录

本仓库 —— 架构层（只陈述原则与约束，不陈述任何要求）：

  governance-architecture.md   为什么这一族是这样分层的

本仓库 —— 规范层（各册陈述其自身主题的要求）：

  organization-governance.md   Organization 主体
  group-collaboration.md       跨域协作
  question.md                  判定格式：四问答成什么样算答出
  naming.md                    命名、引用与版本化
```

剖面层（L4）另有 `assembly.md` 与 `lexicon.md`，叠在下面各层之上；本层入口不逐条索引，见 `README.md` 的层索引。

**各分册彼此并列**；主规范的地位是**不同**：规范性的，而不是信息性的。`governance-architecture.md` 在它们之上一个层面：它解释**为什么这一族是这样分层的**，并且**只陈述原则与约束**；凡需要「必须」的地方，它指向拥有该条的分册（`governance-architecture.md` §1.1）。 每一份回答**不同主体**的**不同问题**：组织可以没有 agent 而存在；agent 可以不属于任何组织而行动；协作跨越组织；记录比它们都活得久。

**治理两册（`organization-governance.md`、`group-collaboration.md`）与架构层同在本仓库**，因为它们的主题不与某个 DID 方法耦合——`governance-architecture.md` 通篇不含 `did:cha2a` 字样，另两册只有身份书写形式与点名的接口点。它们针对一个**身份绑定**书写，本族的方法是其中的工作示例。

| 分册 | 它的主体 | 它回答的问题 | 它读谁 |
|---|---|---|---|
| `agent-identity.md` | **agent** | 它是谁、它能做什么 | `did:cha2a` |
| `organization-governance.md` | **Organization** | 谁有资格授权它 | `agent-identity.md` §7——用来指称*被授权的是什么* |
| `group-collaboration.md` | **协作** | 不同组织的 agent 怎么一起干活 | 上面两份 |
| `evidence-record.md` | **记录** | 做过的事怎么被第三方验证 | `did:cha2a`——用来指称签名者 |
| `question.md` | **判定** | 四问答成什么样算答出、谁判定 | 上面四册——只引用，不重述 |
| `naming.md` | **命名** | 名字从哪来、引用为何必须带校验依据 | `organization-governance.md`（版本化）· `evidence-record.md`（内容标识） |

**「读谁」只表示依赖。** `organization-governance.md` 与 `agent-identity.md` **互相引用**，一棵树表达不了这件事；而树还必须把 `group-collaboration.md` **任意**挂在其中一份下面，可它两份都需要。**§1 的四个条件是并列的，正是同一个道理。**

`EVIDENCE.md` 与 `EVIDENCE_MIN_LOOP.md` 是证据分册的**产物**，不是分册。

**说明**：在本仓库内，除主规范外，其余各册均为 **informative companion document**（见主规范 §11）——规范性要求只在主规范中。**其中 `organization-governance.md` 与 `group-collaboration.md` 陈述其自身主题的要求；`governance-architecture.md` 不陈述任何要求**（其 §1.1）。三者都不是主规范的分册。**「信息性」改变的是地位的性质，而不是地位的高低。**

**一致性测试**不属于本族的分册：它在 `cha2a-conformance` 仓库，其契约由主规范 §9.2 行使。

**语言**：本仓各册英文优先，中文版带 `-zh` 后缀。身份内核仓的两册 companion（`agent-identity`、`evidence-record`）为中文优先，英文版带 `-en` 后缀。

### 读法（建议顺序）

**这是跨越并列者的读法顺序**——上面各册是并列的，这个序列只是穿过它们的一条路径：

| 顺序 | 文档 | 回答的问题 |
|---|---|---|
| 0 | 本文档 | 这一族是干什么的、边界在哪 |
| 1 | `did-method-cha2a.md` | 标识符怎么解析、信任根在哪 |
| 2 | `agent-identity.md` | agent 是谁、能做什么 |
| 3 | `organization-governance.md` | **谁有权授权它** |
| 4 | `group-collaboration.md` | 不同组织的 agent 怎么一起干活 |
| 5 | `evidence-record.md` | 干过的事怎么被独立验证 |
| 6 | `question.md` | 四问答成什么样算答出，以及谁判定 |
| 7 | `naming.md` | 名字从哪来，以及引用为什么必须携带校验依据 |

**顺序 1、2 与 5 在身份内核仓 `did-method-cha2a`；顺序 0、3、4、6、7 在本仓库。**

**够用判据**：一个第一次接触本族的第三方，只凭本册就能说出这一族是什么、边界在哪、按什么顺序读哪几册、哪些能力不属于本族——不需要任何口头补充。满足即止，不再扩写。

## 4. 边界

### 4.1 边界判据

**§1 的四个问题定义核心。** 它们覆盖不到的，就不属于核心——而 §4.2–§4.4 说明那件事**去了哪里**，因为「不在核心里」不等于「没有归属」。

### 4.2 从别处来的——是依赖，不是缺席

| 从哪来 | 为什么 | 关系 |
|---|---|---|
| W3C DID Core / Verifiable Credentials | 标识符与凭证语法 | **复用**——本族不自造任何语法 |
| A2A Task | 任务状态机与消息语义 | **复用**；重定义一处映射（`group-collaboration.md` §8） |
| in-toto | 证据证明的形态 | **复用** |
| 已有的某种传输 | 搬字节 | **复用**——传输不是本族的题目；存在多种，且不要求任何一种 |
| Agent Runtime 与模型 | 执行 | **在模型之外**——Runtime 与信任判断是彼此独立的问题 |

### 4.3 本族采取的立场，以及推迟的

**立场**——这些是关于**本族是什么**的选择，不是缺口：

| 立场 | 为什么 |
|---|---|
| 本族记**事实**与**可下钻的证据**；等级是**信任摘要** | 评分是意见；**发出一个评分，就等于把自己的运营方变成了信任判断的当事方**——这正是 §1 要避免的 |
| 本族提供可核验的事实，**不做背书** | 同一个理由；且在部分法域，「背书」的用词会**改变责任形态并触发许可要求**（§6） |
| 本族定义一种 DID 方法，其他方法**通过映射接入** | 允许其他方法共存；**是否采用本族的方法是各方自己的选择** |

**推迟的**——能力是真的、也是要的，每一项都写明前提：

| 推迟 | 做它的前提 |
|---|---|
| **支付与清算** | 一条 agent 原生的结算路径，且**不要求对端加入某一个运营方的域**。今天在场的持牌枢纽都是受邀制 |
| **市场 / 商店 / 收录** | 一个**承认权留在各方自己手里**（§1 的要求）的分发层 |
| **行为监控 · 内容审计 · 内容合规** | 一个**不需要本族对内容表态**也能评估的披露层 |

**只有「立场」那张表是关于本族是什么的。**「推迟」那张表是**有具名前提的工作**——把它写成边界，是一族**把自己从自己的题目里劝退**的方式。

### 4.4 其余部分落在哪里：Registry 还是应用

**一句话决定：谁能自证，谁就必须自己持有。**

| # | 规则 | 为什么 |
|---|---|---|
| **R1** | Registry 只承载**身份与状态**——DID ↔ DID Document、L0–L4 信任摘要、撤销、组织与成员的状态。它回答「**这是谁、现在还有效吗**」 | §1 四问的第一问 |
| **R2** | **主体能自己签的，就留在主体侧。** Registry 只存指针或哈希，**永不存正文** | `organization-governance.md` §8「保证据、不保正文」的推广 |
| **R3** | **Registry 持有身份与状态；决定在应用侧。** 准入、授权、策略判定都在那里。**Registry 回答，应用决定** | `group-collaboration.md` §5.3——**会做决定的 Registry 就是**本族要消掉的平台断言 |
| **R4** | **协作面——Group、Task、协作记录——属于应用** | `group-collaboration.md` §3 |
| **R5** | **fail-closed 落在判定点。** Registry 报「查不到」或不可达；**拒绝是应用的动作** | `group-collaboration.md` §5.2 |
| **R6** | **跨边界的断言由断言方自己签名。** Registry 只转发与索引，**不代为主体断言**。唯一例外是 DID Document 本身，由 Registry 作为 controller 签 | `did-method-cha2a.md` §4.3–§4.4 |

**落位：**

| 概念 | Registry | 应用 |
|---|---|---|
| DID · DID Document · 密钥 | 解析入口 | 缓存 |
| L0–L4 · `trust/query` · 撤销 | **唯一真源** | 消费 |
| Organization 对象 | **只存指针**（哈希 · 版本 · 状态） | 章程正文 · 角色 · 成员 · controllers |
| 四层回溯背后的**动作**（任命 / 授权 / 撤销） | — | 主体侧执行，留证 |
| Delegation · 授权范围 | — | 凭证在 agent 手里 |
| Group · 成员资格 · 准入 · Presence | — | 协作侧 |
| 任务状态机 | — | 协作侧（A2A） |
| 协作记录 · 账本 · 不一致裁决 | — | 各方自有 |
| Evidence Record | — | 由产生方产出 |
| Break-Glass · 解散 · 根重建 | — | 主体侧执行，留证 |

这些规则是信息性的——它们描述一次合规部署最终必须形成的分工，而要求本身写在所引的各分册里。写在这里，是因为「这块东西归谁持有」是外界对本族提出的第一个问题；**回答得太晚，Registry 就会悄悄变成平台。**

**有一处现成 endpoint 必须把这件事说明白。** 参考 Registry 提供 `GET /api/v1/evidence/query?did=<did>`。按 R2 与 R4，它是**索引 / 指针服务**：它说的是**记录在哪里、其作者的状态是否仍然有效**。它的回答是**一个位置和一个状态**。**验证一条记录靠的是产生方的签名——这是唯一能确立它的东西。**一个既索引证据、又为证据背书的 Registry，就是 §1 所排除的那种一方断言。

## 5. 状态与读法约定

**状态**：Experimental。各分册标注自身状态（draft / 讨论稿）。

**四条读法约定**：

1. **规范性要求只在 `did-method-cha2a.md`**。其余各册的信息性内容不得被当作要求引用。
2. **每一项要么已定、要么标为部署参数、要么标为暂不纳入本版。** 本族不用“留白”当结论，也不用占位数字当结论。已定的项**必须给出推导依据**——推导链可被质疑，而不是只能接受结论；部署参数则固定语义，只把取值留给部署方。**规则陈述为「什么成立、依据是什么」**——不陈述为对错裁决，也不对业界现状作评述。需要排除某样东西时，**写出条件与违反它的后果**，使这个主张可被验证，而不是只能被接受。
3. **实现状态应当被记录**：文档说的能力，若实现尚未做到，应逐条标注状态与日期（而非省略）。
4. **本族与外部对象只有两种关系。** **复用**——本族依赖它——产出**映射表 + 一致性测试**。**不定义**——本族不采用——产出**边界声明 + 一条反例测试：不引入它，最小构建闭环能否跑通**。**不存在第三种叫「对齐」的关系**：它既无产物、又不可证伪；而「某个外部文档已经覆盖了这件事」是关于**别人文档**的判断，**那个判断会错**。**凡本族点名的外部对象，一律记录其状态**——版本 · 日期 · 采纳证据。**由一个项目自行发布、无人采纳的草稿，是同侪草稿，不是权威**：引用它不会把它的分量转移到这里，它的不成熟也同样不构成本族的减分项。**这一条与上位架构 §5 的「五种处置」用的不是同一把尺子。** 本条按**产物**分两类（复用 → 映射表＋一致性测试；不定义 → 边界声明＋反例测试）；上位架构 §5 按**决策阶梯**分五级（采用 → 映射 → 剖面扩展 → 适配 → 自定义）。**两者不互斥**：同一对象先在阶梯上定处置，再按本条定应产出什么。**未定：五级到两类的完整映射。**

**本件的地位**：它是**族入口与索引**，**信息性**的；它**不陈述规范性要求**。四条读法约定是各分册共同遵守的**体例纪律**，写在这里供查阅。规范性要求只在 `did-method-cha2a.md`（上条第 1 项）。

## 6. 术语

| 词 | 本族的用法 |
|---|---|
| **核验**（verification） | 本族描述**对事实的判定**（谁的密钥签的、依据哪条规则、状态如何）。**这是本族的本业** |
| **鉴权 / 登录**（authentication） | 描述**连接层**的身份确认。**避免单独使用“认证”** |
| **认证**（certification） | **不用于指代本族**；仅在引用法规或描述第三方时使用 |
| **信任摘要** | L0–L4 的聚合结果——是“事实的摘要”，不是“评分”或“保证” |
| **委托**（delegation） | 一段有范围、有期限、可撤销的授权关系 |
| **representative** | 在特定上下文中代表某主体的成员 |

> 术语三分（核验 / 鉴权 / 认证）不是措辞洁癖：**“认证”一词在部分法域会触发特定的责任形态与许可要求**。本族的产品与文档一律使用“核验”。
